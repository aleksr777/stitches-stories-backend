# Stitches & Stories — backend

NestJS + PostgreSQL + Redis. Разработка ведётся в ветке `develop`.

Фронтенд: [stitches-stories-frontend](https://github.com/aleksr777/stitches-stories-frontend/tree/develop).
Основа — `aleksr777/nestjs-routing-authorization`; происхождение зафиксировано в [SOURCE-TEMPLATE.md](SOURCE-TEMPLATE.md).

## Запуск для разработки

Нужны Node.js 22+ и Docker Compose.

```bash
git switch develop
npm ci
npm run setup:local
docker compose up -d
npm run migration:run
npm run seed:demo
npm run start:dev
```

`setup:local` создаёт `.env`, если его ещё нет, и генерирует независимые JWT-секреты и случайный пароль владельца. Существующий `.env` не перезаписывается. При обновлении старого `.env` сопоставьте настройки с `.env.example` вручную.

- API: `http://localhost:5174/api`.
- PostgreSQL: `localhost:5432`, база `stitches_stories`, пользователь `postgres`; пароль для локальной базы задан в compose и `.env.example`.
- Redis: `localhost:6379`.
- Mailpit SMTP: `localhost:1025`; просмотр тестовых писем: `http://localhost:8025`.
- Для входа владельца используйте `INITIAL_ADMIN_EMAIL` и `INITIAL_ADMIN_PASSWORD` из локального `.env`. Миграция создаёт владельца; публичная регистрация никогда не назначает роль администратора.

Compose предназначен для локальной разработки: порты привязаны к loopback, тестовые SMTP и пароль базы не подходят для рабочего размещения. Dockerfile собирает API; миграции выполняются отдельно до старта.

## Сценарии магазина

- Каталог и карточки изделий хранятся в PostgreSQL. Демонстрационные позиции исключены из production-выдачи.
- `POST /api/shop/requests` принимает предварительную заявку, проверяет цену и доступное количество. Повторный запрос с тем же UUID и телом возвращает тот же результат; изменение тела при уже использованном ключе — HTTP 409.
- Сумма рассчитывается сервером в целых рублях. Заявка не принимает платёж и не резервирует остаток.
- Зарегистрированный покупатель видит только заявки, отправленные из своего аккаунта; заявки гостей не привязываются по неподтверждённому адресу почты.
- Регистрация подтверждается кодом из письма. Имя и две отдельные ссылки на версии документов сохраняются в Redis до подтверждения; пользователь и события согласий создаются в одной транзакции PostgreSQL.
- Подписка на рекламу подтверждается отдельной одноразовой ссылкой. Хеши токенов, срок действия и события согласий сохраняются на сервере. Отписка доступна по ссылке из письма и из кабинета.
- Отзыв согласия на кабинет закрывает профиль и сеансы; независимая подписка управляется отдельно. Сроки хранения заявок и доказательств согласий должны быть утверждены перед запуском.
- Владелец управляет карточками и статусами заявок через защищённые `/shop/admin/*`.

## Основные маршруты

| Метод              | Путь после `/api`                                            | Доступ                                   |
| ------------------ | ------------------------------------------------------------ | ---------------------------------------- |
| GET                | `/shop/products`, `/shop/products/:slug`                     | Открытый каталог                         |
| GET                | `/legal/documents`, `/legal/documents/:id/versions/:version` | Текущие и архивные документы             |
| POST               | `/auth/registration/request`                                 | `email`, `password`, `name`, `documents` |
| POST               | `/auth/registration/confirm`                                 | `email`, `code`                          |
| POST               | `/shop/requests`                                             | Гость либо Bearer-токен                  |
| GET                | `/shop/me/requests`, `/shop/me/favorites`                    | Свой аккаунт                             |
| POST / DELETE      | `/shop/me/favorites/:id`                                     | Свой аккаунт                             |
| GET                | `/shop/me/consents`, `/legal/me/events`                      | Свои согласия                            |
| POST               | `/shop/me/consents/withdraw`                                 | `purpose`: `account` или `marketing`     |
| POST               | `/shop/newsletter/request`                                   | `email`, две ссылки на документы         |
| POST               | `/shop/newsletter/confirm`, `/shop/newsletter/unsubscribe`   | Одноразовый/отписной `token`             |
| GET / POST / PATCH | `/shop/admin/products`, `/shop/admin/products/:id`           | Только admin                             |
| GET / PATCH        | `/shop/admin/requests`, `/shop/admin/requests/:id`           | Только admin                             |

Ссылка на документ — `{ id, version, sha256 }` из `/legal/documents`. Для регистрации нужны `pd-account` и `account-terms`; для рассылки — `pd-marketing` и `ads-email`; для заявки — `offer`. Устаревшие версии отвергаются.

## Документы и готовность к запуску

В `src/legal/documents.json` сохранены 11 проектов из согласованного комплекта. Это не заключение о юридической готовности магазина. Перед запуском нужно заполнить сведения о продавце и сервисах, проверить условия обработки/хранения данных, обращения и документы на изделия.

После согласования текста укажите новую `version`, заполните фактические поля и статус `published`, затем выполните `npm run legal:hash`. Содержимое уже сохранённой версии менять нельзя: сервис проверяет неизменность по SHA-256. `NODE_ENV=production` блокирует запуск с проектами документов или известными незаполненными полями. Не обходите этот контроль переводом рабочего сервера в development.

Реальный эквайринг, автоматическое формирование чеков НПД, доставка, загрузка фотографий, уведомления владельца о новых заявках и регламентная очистка заявок/журнала согласий пока не реализованы. Новые заявки доступны в кабинете владельца. Аналитика не подключена.

Предыдущие правовые материалы: [перечень требований](RF-REQUIREMENTS-NPD.md), [примечания к проектам](LEGAL-REVIEW-RU.md). Они сохранены как исходные материалы и требуют проверки перед запуском реального магазина.

## Проверка

```bash
npx tsc --noEmit --noUnusedLocals --noUnusedParameters
npx eslint "{src,apps,libs,test}/**/*.ts"
npm run build
npm test -- --runInBand
npm run test:e2e -- --runInBand
```

Для интеграционных тестов задайте `TEST_DATABASE_URL` на отдельную тестовую PostgreSQL. Тесты создают и удаляют только свои случайные схемы. Без этой переменной PostgreSQL-наборы пропускаются. CI задаёт её и проверяет миграции, транзакции заявок, раздельные согласия и сессии.

`npm run test:smoke` проверяет запущенный тестовый API: readiness, каталог, запрет регистрации без согласий, права администратора, проверку цен и отсутствие дубликата заявки. Скрипт создаёт явно тестовую заявку и должен запускаться только в тестовой среде. CI поднимает PostgreSQL/Redis и запускает эту проверку после миграций и демо-наполнения.
