# Stitches & Stories — backend

NestJS + PostgreSQL + Redis. Разработка ведётся в ветке `develop`.

Фронтенд: [stitches-stories-frontend](https://github.com/aleksr777/stitches-stories-frontend/tree/develop).
Основа — `aleksr777/nestjs-routing-authorization`; происхождение зафиксировано в [SOURCE-TEMPLATE.md](SOURCE-TEMPLATE.md).

## Запуск для разработки

Нужны Node.js 22+ и Docker Compose.

```bash
git switch develop
npm ci
npm run setup:local
docker compose up -d --wait
npm run migration:run
npm run seed:demo
npm run start:dev
```

`setup:local` создаёт `.env`, если его ещё нет, и генерирует независимые JWT-секреты и случайный пароль владельца. Существующий `.env` не перезаписывается. При обновлении старого `.env` сопоставьте настройки с `.env.example` вручную.

Для локальной разработки те же действия можно выполнить одной командой после `npm ci`:

```bash
npm run start:local
```

Она создаёт или обновляет локальные порты `.env`, ожидает готовности Docker-сервисов, запускает миграции, демо-наполнение и API. При ошибке любого шага следующие шаги не выполняются, поэтому после сбоя Docker миграции не попадут в другую базу на занятом стандартном порту. Если API уже работает, сначала остановите его.

- API: `http://localhost:5174/api`.
- PostgreSQL: `127.0.0.1:15432`, база `stitches_stories`, пользователь `postgres`; пароль для локальной базы берётся из `DB_PASSWORD` в `.env`.
- Redis: `127.0.0.1:16379`.
- Mailpit SMTP: `127.0.0.1:11025`; просмотр тестовых писем: `http://127.0.0.1:18025`.
- Для входа владельца используйте `INITIAL_ADMIN_EMAIL` и `INITIAL_ADMIN_PASSWORD` из локального `.env`, затем подтвердите вход шестизначным кодом из письма. Миграция создаёт владельца; публичная регистрация никогда не назначает роль администратора.

Compose предназначен для локальной разработки: порты привязаны к loopback, тестовые SMTP и пароль базы не подходят для рабочего размещения. Dockerfile собирает API; миграции выполняются отдельно до старта.

### Если порты заняты или `.env` создан предыдущей версией

Публикуемые порты PostgreSQL и Redis и подключения приложения используют одни значения из `.env`: `DB_PORT`, `REDIS_PORT`. У Mailpit отдельные `MAILPIT_SMTP_PORT` и `MAILPIT_WEB_PORT`: внешняя почта приложения (`SMTP_HOST`, `SMTP_PORT`) не меняет порты контейнера Mailpit. Внутренние порты контейнеров остаются стандартными. Если выбранный порт тоже занят, укажите свободный в `.env`. При использовании Mailpit как SMTP-сервера приложения его `SMTP_PORT` должен совпадать с `MAILPIT_SMTP_PORT`.

После обновления репозитория выполните:

```bash
git pull --ff-only origin develop
npm run setup:local -- --repair-ports
docker compose up -d --wait
docker compose ps
npm run migration:run
npm run seed:demo
npm run start:dev
```

Запускайте следующую команду только после успешного завершения предыдущей; `npm run start:local` выполняет эти шаги с автоматической остановкой при ошибке. `--repair-ports` обновляет стандартные порты старого локального `.env` на указанные выше, заменяет локальные адреса на `127.0.0.1` и добавляет порты Mailpit. Существующие нестандартные порты, реквизиты БД, JWT-секреты и все параметры владельца сохраняются. Перед изменением создаётся резервная копия `.env.backup-*`, исключённая из Git. Она содержит секреты, как и `.env`; её не следует публиковать.

Внешний SMTP, в том числе Яндекс, разрешён: его `SMTP_*` остаются без изменений. Для локального Mailpit без TLS и авторизации обновляются только старые адрес и порт SMTP. Скрипт отказывается менять production или удалённые PostgreSQL/Redis и указывает конкретное мешающее поле. Остановите работающий API перед изменением подключений. Контейнеры этого проекта пересоздаются при изменении портов, том `postgres_data` сохраняется.

### Если используется Яндекс SMTP

`smtp.yandex.com`, порт `465` и `SMTP_SECURE=true` соответствуют [настройкам Яндекс Почты](https://yandex.com/support/yandex-360/customers/mail/en/mail-clients/others). В `SMTP_PASS` нужен пароль приложения для почты; SMTP должен быть разрешён в настройках аккаунта. Эти данные указываются только в локальном `.env`. Такой режим отправляет реальные письма через Яндекс; Mailpit их не перехватывает. Адрес администратора `INITIAL_ADMIN_EMAIL` может отличаться от `SMTP_FROM`.

Параметры `INITIAL_ADMIN_*` применяются миграцией при создании владельца. Изменение пароля в `.env` после выполнения этой миграции не меняет пароль уже созданного аккаунта; используйте смену или восстановление пароля в приложении.

`Bind ... port is already allocated` означает, что опубликованный порт занят. `password authentication failed` означает, что PostgreSQL доступен, но отклоняет реквизиты: это может быть другая локальная база или сохранённый том с другим паролем. Проверьте адрес своего контейнера:

```bash
docker compose ps
docker compose port postgres 5432
docker compose port redis 6379
```

При настройках по умолчанию адреса должны быть `127.0.0.1:15432` и `127.0.0.1:16379`. Не выполняйте `docker compose down -v` для устранения ошибки: эта команда удаляет данные. Изменение `DB_PASSWORD` в `.env` не меняет пароль в уже инициализированном томе PostgreSQL. Если адрес правильный, а пароль по-прежнему отклоняется, используйте пароль существующей базы и отдельно разберите её конфигурацию. Не отправляйте содержимое `.env` в чат или GitHub.

Правила подстановки `.env`: [документация Docker Compose](https://docs.docker.com/compose/how-tos/environment-variables/variable-interpolation/).

## Сценарии магазина

- Каталог и карточки изделий хранятся в PostgreSQL. Демонстрационные позиции исключены из production-выдачи.
- `POST /api/shop/requests` принимает предварительную заявку, проверяет цену и доступное количество. Повторный запрос с тем же UUID и телом возвращает тот же результат; изменение тела при уже использованном ключе — HTTP 409.
- Сумма рассчитывается сервером в целых рублях. Заявка не принимает платёж и не резервирует остаток.
- Зарегистрированный покупатель видит только заявки, отправленные из своего аккаунта; заявки гостей не привязываются по неподтверждённому адресу почты.
- Регистрация подтверждается кодом из письма. Имя и две отдельные ссылки на версии документов сохраняются в Redis до подтверждения; пользователь и события согласий создаются в одной транзакции PostgreSQL.
- Вход владельца требует пароль и отдельный шестизначный код из письма. До подтверждения кода access- и refresh-токены не выдаются; код действует 5 минут, а лимит попыток и повторной отправки хранится в Redis.
- Подписка на рекламу подтверждается отдельной одноразовой ссылкой. Хеши токенов, срок действия и события согласий сохраняются на сервере. Отписка доступна по ссылке из письма и из кабинета.
- Отзыв согласия на кабинет подтверждается текущим паролем, закрывает профиль и все его сеансы; независимая подписка управляется отдельно. Сроки хранения заявок и доказательств согласий должны быть утверждены перед запуском.
- Владелец управляет карточками и статусами заявок через защищённые `/shop/admin/*`.

| Метод                       | Путь после `/api`                                            | Доступ                                   |
| --------------------------- | ------------------------------------------------------------ | ---------------------------------------- |
| GET                         | `/shop/products`, `/shop/products/:slug`                     | Открытый каталог                         |
| GET                         | `/legal/documents`, `/legal/documents/:id/versions/:version` | Текущие и архивные документы             |
| POST                        | `/auth/registration/request`                                 | `email`, `password`, `name`, `documents` |
| POST                        | `/auth/registration/confirm`                                 | `email`, `code`                          |
| POST                        | `/auth/login/admin/confirm`, `/auth/login/admin/resend`       | Подтверждение входа владельца             |
| POST                        | `/shop/requests`                                             | Гость либо Bearer-токен                  |
| GET                         | `/shop/me/requests`, `/shop/me/favorites`                    | Свой аккаунт                             |
| POST / DELETE               | `/shop/me/favorites/:id`                                     | Свой аккаунт                             |
| GET                         | `/shop/me/consents`, `/legal/me/events`                      | Свои согласия                            |
| POST                        | `/shop/me/consents/withdraw`                                 | `purpose`; для `account` — текущий пароль |
| POST                        | `/shop/newsletter/request`                                   | `email`, две ссылки на документы         |
| POST                        | `/shop/newsletter/confirm`, `/shop/newsletter/unsubscribe`   | Одноразовый/отписной `token`             |
| GET / POST / PATCH / DELETE | `/shop/admin/products`, `/shop/admin/products/:id`           | Только admin                             |
| GET                         | `/shop/images/:id`                                           | Фотографии опубликованных изделий        |
| GET                         | `/shop/admin/images/:id`                                     | Только admin, включая скрытые изделия    |
| GET / PATCH                 | `/shop/admin/requests`, `/shop/admin/requests/:id`           | Только admin                             |

Ссылка на документ — `{ id, version, sha256 }` из `/legal/documents`. Для регистрации нужны `pd-account` и `account-terms`; для рассылки — `pd-marketing` и `ads-email`; для заявки — `offer`. Устаревшие версии отвергаются.

## Фотографии изделий

В форме создания и редактирования изделия администратор выбирает файлы с компьютера, просматривает их, назначает основное фото и сохраняет изделие. Допускаются до 8 статических фотографий JPEG, PNG или WebP, каждая до 8 МБ и 40 мегапикселей. Сервер проверяет содержимое и декодирование изображения, а не только расширение. Оригинальные байты сохраняются без изменения в `product_image.data` (PostgreSQL `bytea`), с принадлежностью изделию, форматом, размерами и SHA-256. Резервная копия PostgreSQL должна включать эту таблицу.

После обновления бэкенда выполните `npm ci` (добавлена библиотека проверки изображений `sharp`) и `npm run migration:run`, затем перезапустите API. Миграция `CreateProductImages1789650000000` добавляет таблицу фотографий; существующие изделия и их статические пути сохраняются.

`POST /shop/admin/products` и `PATCH /shop/admin/products/:id` принимают `multipart/form-data`: поле `data` содержит JSON карточки, повторяемое поле `files` — файлы. В `data.images` укажите `upload:0`, `upload:1` и т. д. в порядке файлов либо сохранённые `/shop/images/<uuid>` этого изделия. Порядок массива определяет основное фото. Обычный JSON без новых файлов также поддерживается, как и прежние пути `/images/имя.jpg`.

Изделие, новые изображения и удаление убранных фотографий сохраняются в одной транзакции. При ошибке данные остаются прежними; закрытие формы до сохранения ничего не загружает. `DELETE /shop/admin/products/:id` удаляет само изделие, его фотографии и записи избранного; уже отправленные заявки сохраняют свой снимок изделия и не меняются. Каталог возвращает только пути, сами изображения загружаются отдельными запросами из API. Публичная выдача проверяет видимость изделия при каждом запросе (в production также исключает демо); для предпросмотра скрытых изделий администратор использует защищённый маршрут. Загрузка, редактирование и удаление требуют роли admin. Если перед API установлен reverse proxy, его лимит тела запроса должен допускать суммарный multipart до 65 МБ; ограничения каждого файла проверяет приложение.

## Документы и готовность к запуску

В `src/legal/documents.json` сохранены 11 проектов из согласованного комплекта. Это не заключение о юридической готовности магазина. Перед запуском нужно заполнить сведения о продавце и сервисах, проверить условия обработки/хранения данных, обращения и документы на изделия.

После согласования текста укажите новую `version`, заполните фактические поля и статус `published`, затем выполните `npm run legal:hash`. Содержимое уже сохранённой версии менять нельзя: сервис проверяет неизменность по SHA-256. `NODE_ENV=production` блокирует запуск с проектами документов или известными незаполненными полями. Не обходите этот контроль переводом рабочего сервера в development.

Реальный эквайринг, автоматическое формирование чеков НПД, доставка, уведомления владельца о новых заявках и регламентная очистка заявок/журнала согласий пока не реализованы. Новые заявки доступны в кабинете владельца. Аналитика не подключена.

Предыдущие правовые материалы: [перечень требований](RF-REQUIREMENTS-NPD.md), [примечания к проектам](LEGAL-REVIEW-RU.md). Они сохранены как исходные материалы и требуют проверки перед запуском реального магазина.

## Проверка

```bash
npx tsc --noEmit --noUnusedLocals --noUnusedParameters
npx eslint "{src,apps,libs,test}/**/*.ts"
npm run build
npm test -- --runInBand
npm run test:e2e -- --runInBand
npm run test:setup
```

Для интеграционных тестов задайте `TEST_DATABASE_URL` на отдельную тестовую PostgreSQL. Тесты создают и удаляют только свои случайные схемы. Без этой переменной PostgreSQL-наборы пропускаются. CI задаёт её и проверяет миграции, транзакции заявок, раздельные согласия и сессии.

`npm run test:smoke` проверяет запущенный тестовый API: readiness, каталог, запрет регистрации без согласий, права администратора, проверку цен, отсутствие дубликата заявки и загрузку/чтение/удаление фотографий с проверкой скрытого изделия. Скрипт создаёт явно тестовые заявку и изделие и должен запускаться только в тестовой среде. CI поднимает PostgreSQL/Redis и запускает эту проверку после миграций и демо-наполнения. Отдельные тесты фотографий проверяют реальный multipart, ограничения файлов, доступы и транзакционное хранение в PostgreSQL.
